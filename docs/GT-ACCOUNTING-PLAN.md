# GT ACCOUNTING — план розробки

**Модуль 02 платформи GT.** Стек той самий: vanilla JS + Supabase + GitHub Pages.
Статус: планування. Дата: 14.08.2026

---

## 1. Головне рішення перед стартом

**Хто платить.** Дослідження ринку дало чітку відповідь: ФОП платить неохоче (150–300 грн/міс — стеля), а бухгалтер-аутсорсер веде 30–50 клієнтів і платить значно охочіше, бо економить години щомісяця.

**Висновок: цільовий користувач — бухгалтер, який обслуговує багато ФОПів.** Це змінює архітектуру з першого дня: не «один акаунт = один ФОП», а «один акаунт = багато компаній із перемиканням між ними».

Сам ФОП теж користується — просто в нього одна компанія в списку. Той самий код, різні тарифи.

**Чого не робимо на старті:** звітності до ДПС, повного бухобліку, проведень, ПДВ-декларацій. Там сидять M.E.Doc і Dilovod з десятиліттями напрацювань. Наша територія — **первинка за 30 секунд**.

## 2. Що таке «натиснув і готово»

Один сценарій, доведений до ідеалу. Решта — навколо нього.

```
Обираю контрагента  →  обираю послугу  →  [СТВОРИТИ РАХУНОК]  →  PDF готовий
       ↑                      ↑
  вже в базі            вже в базі
  (або код ЄДРПОУ       (свій прайс)
   і дані підтяглись)
```

Три кліки замість заповнення бланка. Далі — акт із того самого рахунку одним кліком.

**Головна «вау»-фіча першого релізу:** вводиш ЄДРПОУ або ІПН — назва, адреса, керівник підтягуються самі. Людина одразу бачить, що система працює за неї.

## 3. Структура бази (Supabase)

Схема `acct`. RLS на кожній таблиці **з першого дня** — без винятків.

### Ядро

**`acct.companies`** — компанії, від імені яких виставляємо документи
```
id, owner_id (auth.users), name, legal_type (fop|tov),
edrpou, ipn, tax_group, vat_payer (bool), tax_rate,
iban, bank_name, address, phone, email,
director_name, signature_url, stamp_url,
created_at, is_active
```

**`acct.counterparties`** — контрагенти (кому виставляємо)
```
id, company_id → companies, name, legal_type,
edrpou, ipn, iban, bank_name, address, phone, email,
director_name, notes, source (manual|edr), created_at
```

**`acct.services`** — прайс компанії
```
id, company_id, name, unit, price, vat_rate, is_active
```

### Документи

**`acct.documents`** — усі типи в одній таблиці
```
id, company_id, counterparty_id, contract_id (nullable),
doc_type (invoice|act|waybill|offer),
number, doc_date, subject,
subtotal, vat_amount, total, total_words,
status (draft|issued|sent|paid|partial|overdue|cancelled),
parent_doc_id (акт посилається на рахунок),
pdf_url, signed_url, sign_status,
created_by, created_at, updated_at
```

**`acct.document_items`** — позиції
```
id, document_id, position, name, unit, qty, price,
vat_rate, amount, vat_amount, total
```

**`acct.contracts`**
```
id, company_id, counterparty_id, number, contract_date,
subject, amount, is_recurring, recurring_amount, recurring_day,
valid_from, valid_to, status, pdf_url, template_id
```

**`acct.numbering`** — лічильники номерів
```
company_id, doc_type, year, prefix, next_number
```
Номер видається атомарно через RPC-функцію, інакше при паралельній роботі будуть дублі.

### Гроші

**`acct.payments`**
```
id, company_id, document_id (nullable), amount, payment_date,
direction (in|out), source (manual|mono|privat),
bank_tx_id (унікальний, щоб не задвоїти), counterparty_name,
description, matched_by (auto|manual), created_at
```

### Службові

**`acct.audit_log`** — хто, коли, що змінив
```
id, company_id, user_id, entity, entity_id,
action (create|update|delete|sign|send), diff (jsonb), created_at
```

**`acct.company_access`** — доступ бухгалтера до чужих компаній
```
company_id, user_id, role (owner|accountant|manager|viewer), granted_at
```

### RLS — принцип

Доступ до будь-якого рядка тільки якщо `company_id` є в `company_access` для поточного `auth.uid()`. Одна SQL-функція `has_company_access(company_id)`, яка викликається в кожній політиці. Не дублювати логіку в 10 місцях.

**Перевірка перед релізом:** зайти під тестовим акаунтом і спробувати витягнути чужі документи прямим запитом до API. Має повернути порожньо.

## 4. Двигун документів

Один шаблонізатор на всі типи, а не окремий код під кожен документ.

```
Шаблон (HTML) + Дані (JSON) → HTML A4 → друк / PDF
```

- Шаблони зберігати як HTML-рядки з плейсхолдерами `{{company.name}}`, `{{#items}}...{{/items}}`
- Друк — через `window.print()` з `@media print`, як у GT Tires. Працює всюди, нічого не важить
- PDF — через ту саму сторінку друку («Зберегти як PDF» у діалозі браузера). Окрема бібліотека потрібна тільки коли доведеться відправляти файл на email автоматично

**Обов'язкові реквізити первинного документа** (ст. 9 Закону 996-XIV): назва документа, дата, назва суб'єкта, зміст і обсяг операції, одиниця виміру, посади та підписи. Це має бути в шаблоні акта й накладної жорстко, не опційно.

**Сума прописом** — окрема функція, українською, з правильними відмінками. Дрібниця, але без неї документ не виглядає справжнім.

## 5. Етапи

### Етап 0 · Валідація (1–2 тижні, до написання коду)

Поговорити з 5–7 бухгалтерами й 10 ФОПами. Одне питання: скільки часу на місяць з'їдає виписування рахунків і актів, і що вони використовують зараз.

**Іти далі, якщо:** щонайменше половина скаржиться на ручну роботу, і хоча б троє кажуть, що заплатили б.
**Не йти далі, якщо:** усі вже сидять у Taxer/Dilovod і не бачать проблеми.

### Етап 1 · Рахунок за 30 секунд (3–4 тижні)

Мінімум, який уже можна показувати й продавати.

- Реєстрація, картка своєї компанії
- Довідник контрагентів + **автозаповнення за ЄДРПОУ/ІПН**
- Прайс послуг
- Створення рахунку: контрагент → позиції → сума → PDF
- Автонумерація
- Друк A4 і збереження в PDF
- Список документів зі статусами

**Готово, коли:** можна виставити реальний рахунок реальному клієнту й він його оплатить.

### Етап 2 · Акти й договори (2–3 тижні)

- Акт із рахунку одним кліком (дані переносяться, номер новий)
- Видаткова накладна
- Конструктор договорів: 3–4 готові шаблони (обслуговування, разові послуги, поставка)
- Ручна відмітка «Оплачено» + статуси прострочення

### Етап 3 · Гроші автоматично (3–4 тижні)

- Підключення monobank за токеном (API безкоштовне)
- ПриватБанк через «Автоклієнт»
- Автозвірка: прийшла сума → знаходимо рахунок → статус «Оплачено»
- Дебіторка: хто скільки винен і скільки днів
- Нагадування в Telegram (бот уже є)

**Це головна відмінність від простих генераторів рахунків.** Тут з'являється справжня цінність.

### Етап 4 · Підписи (3–4 тижні)

- **Дія.Підпис** — клієнт підписує договір у себе в телефоні. Інтеграція безкоштовна, заявка через `start@diia.gov.ua`
- **DepositSign** — хмарний КЕП для підписання зі свого боку. Ціна ключа від 780 грн/рік
- Статуси: підписано / надіслано / прийнято

### Етап 5 · Кабінет бухгалтера (2–3 тижні)

- Перемикач компаній угорі
- Зведена панель: у кого що прострочено по всіх клієнтах одразу
- Податковий календар з нагадуваннями
- Ролі й журнал дій

## 7. Ризики

**Юридичний.** Ніде не писати «система веде бухгалтерію відповідно до законодавства». Формулювання: «інструмент для формування документів». Відповідальність за зміст — на користувачі. Це прямо в договорі оферти.

**Правила змінюються.** Ставки ЄСВ, ліміти груп, форми документів — усе це рухається щороку. Тримати в окремій таблиці-довіднику з датами дії, а не зашивати в код.

**Витік даних.** Бухгалтерська база — це реквізити й обороти десятків компаній. RLS з першого дня, MFA для тарифів від «Бухгалтера», журнал входів. Тут не можна повторити історію з ключами.

**Розпорошення.** Спокуса зробити «все одразу» вб'є проєкт. Етап 1 має вийти живим до того, як почнеться Етап 2.

**Опендатабот платний.** Автозаповнення за ЄДРПОУ — платне API. Порахувати вартість запиту й закласти ліміт на безкоштовному тарифі.

## 8. Найближчі кроки

1. **Провести валідацію** — 5 розмов, тиждень
2. Написати SQL-схему `acct` з RLS і прогнати перевірку доступу
3. Зробити двигун документів окремим файлом і протестувати на рахунку
4. Зібрати Етап 1 як `gt-accounting.html` у тому ж репозиторії
5. Виставити перший реальний рахунок через систему

**Принцип роботи той самий: один крок — одна перевірка — узгодження.** Хірург, не трактор.
